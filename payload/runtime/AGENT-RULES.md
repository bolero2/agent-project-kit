# Agent 공통 규칙 (local-only)

> 이 프로젝트에 설치된 모든 커스텀 Agent(review-killer, reviewer, developer 등)가 가동
> 직후 정독하고 준수해야 하는 공통 계약이다. `CONTEXT.md`의 공통 규칙에 더해 적용된다.

## 가동 절차

1. Agent는 사용자의 트리거 문구로만 가동한다. 세션 시작만으로 자동 가동하지 않는다.
2. 가동 즉시 순서대로 정독한다: `AGENTS.md`(포인터 `CLAUDE.md` 포함) →
   `.agent-project-kit/CONTEXT.md` → `.agent-project-kit/HANDOFF.md`.
3. 저장소의 markdown 문서 트리를 recursive하게 탐색해 목록을 파악하고, **작업 대상과 관련된
   문서만** 추가 정독한다. 관련 없는 문서까지 전부 정독하지 않는다.
4. 문서를 읽고도 모르는 것은 관련 코드를 구체적으로 확인한 뒤, 그래도 모호하면 사용자에게
   질문한다.
5. 종료는 사용자의 작업 종료 요청 또는 세션 종료 시점이며, 종료 전 문서 갱신 절차를 수행한다.

## 대기·폴링 실행 방식

- "대기(idle)"는 turn을 끝내고 사용자 알림을 기다리는 것이 **아니다**. "티켓을 옮기면
  알려주세요", "리뷰가 올라오면 말씀해 주세요"라고 말하고 멈추는 것은 **실패 동작**이다.
  이벤트(리뷰·티켓)는 Agent가 도구 호출 폴링으로 스스로 감지한다.
- 셸로 확인 가능한 신호(gh 등)는 sleep과 확인을 묶은 **단일 blocking 스크립트를 1회 Bash
  호출**해 기다린다(감지 시 즉시 종료하는 루프). MCP로만 확인 가능한 신호(Jira 등)는
  `sleep <간격>` Bash 호출과 조회 호출을 한 라운드로 묶어 turn을 끝내지 않고 반복한다.
- 폴링 중에는 사용자에게 중간 보고하지 않는다. 감지 → 처리 → 폴링 복귀.
- 정의된 타임아웃/상한이 소진되었을 때만 현재 상태와 재개 트리거를 남기고 종료한다.
  컨텍스트 한도가 가까워지면 HANDOFF에 상태를 남기고 재가동을 요청한다.
- 호스트 세션은 트리거를 받으면 해당 Agent를 subagent로 가동해 이 규칙대로 돌게 한다.
  호스트가 직접 "기다리겠다"며 turn을 끝내지 않는다.

## 명확성 원칙 (최우선)

- 모르는 것, 모호한 것, 사용자 판단이 필요한 것은 반드시 질문한다.
- 질문한 항목은 답을 받을 때까지 보류 상태로 유지한다. 임의 판단으로 다음 단계로 넘어가거나
  다른 결론으로 대체하지 않는다.
- 근거 없는 추정으로 행동하지 않는다. 가설은 가장 작은 검증으로 확인한 뒤에만 사실로 쓴다.

## 작업 범위

- 사용자가 명시한 범위(예: "백엔드 쪽 코드 수정")만 수정한다.
- 세션 컨텍스트로 범위를 추정할 수 있으면 참고하되, 확신이 없으면 질문한다.
- 범위 외 코드 수정은 금지한다. 범위 외 원인을 발견하면 수정하지 말고 파일·라인 근거와 함께
  보고만 한다.

## Git 규칙

- commit/push/PR 생성은 soln-va-tools 마켓플레이스 스킬(`commit`, `create-pr` 등)이 설치되어
  있으면 **반드시** 그것을 경유한다. 스킬이 있는데 직접 `git commit`/`gh pr create`를 실행하는
  것은 금지다. 스킬 부재를 확인한 경우에만 자체 수행한다.
- 스킬의 출력 규약을 바꾸지 않는다. 예: create-pr 스킬이 PR 제목에 `[DF-810]` 같은 Jira 티켓
  prefix를 붙이는 것은 **정상 규약**이므로 그대로 따른다.
- 한 커밋 = 하나의 변경 이유 + 그 변경을 완성하는 코드와 테스트. 최소 기능 단위로 최대한
  잘게 쪼개고, 필요하면 더 쪼갠다.
- force-push, force-commit 등 파괴적/준-파괴적 행동은 절대 금지한다(킷 guard도 차단한다).
- conflict 해소는 base 브랜치를 feature 브랜치로 merge하는 방식을 우선한다. merge로 정말
  해소가 불가능한 경우에만 rebase를 허용하며, 그 경우에도 force-push는 금지한다.
- merge는 직접 수행하지 않는다. "머지 가능합니다"로 사용자에게 통보만 한다.
- **브랜치명에만** Jira 티켓 번호를 넣지 않는다 — `feat/<slug>`, `fix/<slug>` 형태로 짓는다.
  커밋 메시지·PR 제목·description은 사용하는 스킬/프로젝트 규약을 따른다(PR 제목의 Jira
  prefix, description의 Jira 링크 모두 허용).
- PR 생성 시 API의 신규/변경/삭제가 있으면 PR description에 반드시 기재한다.

## QA 규칙

### 검증 방법

- push/PR 전에 수정한 단위 기능을 검증한다.
- docker화된 웹 서비스면 docker compose로 기동한 뒤 Playwright MCP로 화면 QA를 수행한다.
- Python 프로젝트면 pytest 실행은 필수다.
- 위 두 조건(docker화된 웹 서비스, Python 프로젝트) 중 어느 것에도 해당하지 않으면
  "docker화된 서비스가 아닙니다. QA를 어떻게 진행할까요?"를 질문하고, 받은 답을 CONTEXT의
  프로젝트 로컬 메모(QA 방법)에 기록해 이후 세션에서 재사용한다.

### QA 증거

- **PR을 만들 때는 항상** 그 PR에서 구현·수정한 기능을 빠짐없이 QA하고 증거를 PR 본문(Test
  plan)에 첨부한다. 기능마다 **정상 경로와 주요 실패 경로**를 함께 보인다. 판정 근거가 되는 것은
  전부 증거다 — 화면, API 요청·응답, 큐·DB·스토리지 상태, 로그 발췌.
- 리뷰 대응 코멘트에서 QA를 근거로 쓰거나, 리뷰가 "실환경 검증"·"실제 동작 확인"을 요구하면
  그 대응 코멘트에도 QA 증거를 첨부한다. 텍스트 주장("테스트했다")만으로는 리뷰어가 확인할 수 없다.
- 증거 수준은 CONTEXT 로컬 메모의 `QA 증거 수준`을 따른다(기본: 스크린샷 필수). `QA 기준 예시
  링크`가 있으면 매번 그 예시를 참고해 기능 단위로 더 발전시킨다.
- 품질 기준 5가지:
  1. **실제 화면 캡처** — 화면이 있으면 실제 화면을 찍는다(관리 UI·대시보드 포함). 가공한
     화면으로 대신하지 않는다.
  2. **API는 텍스트와 이미지 둘 다** — 요청(메서드·URL·헤더 이름·본문)과 응답(상태 코드·본문)을
     코드 블록 텍스트로 싣고, 같은 내용을 이미지로도 싣는다.
  3. **재현 가능한 명령** — 각 장면을 만든 명령을 그대로 적고(비밀값은 `<변수>`), 값은
     `항목 = 값 (해석)` 형태로 적는다. 예: `memory limit` = `1073741824` (1.00 GiB).
  4. **흐름 테스트는 순서와 입출력** — "A 실행 → B 실행 → …"을 번호로 적고 단계마다
     input/output을 보인다.
  5. **실행 시각** — 단계·장면마다 실행 timestamp를 찍고 기준 시간대를 밝힌다. 경과 시간이
     판정 근거면 기준 시각 대비 `+Ns`로도 적는다.
- 명령·수치는 본문 텍스트로도 남긴다. 이미지만으로 판정 근거를 대신하지 않는다.
- 게시 전 마스킹(필수): 토큰·비밀번호·접속 URL의 자격증명·presigned 서명·내부 IP·개인정보가
  보이면 가리거나 다시 찍는다.
- **이미지를 저장소에 커밋하지 않는다.** 원본은 로컬 작업 경로에 두고 코멘트에 그 경로를 적는다.
- 첨부가 안 될 때: 도구·환경이 이미지 첨부를 지원하지 않으면(브라우저 도구가 없는 Agent 도구,
  로그인 불가 등) 텍스트 증거(명령·수치·증거 경로)로 대신하고 해당 본문·코멘트에
  `스크린샷 첨부 불가: <사유>`를 적는다. 사용자에게는 종료 보고에서 알린다.

## 브라우저 작업과 사용자 도움

- **Agent의 브라우저 작업은 항상 분리된 브라우저에서만 한다** — 브라우저 자동화 도구(예:
  Playwright MCP)가 띄우는 별도 브라우저·별도 프로세스. **사용자가 쓰고 있는 브라우저(확장으로
  사용자 브라우저를 조작하는 도구 등)는 쓰지 않는다.** 사용자가 그동안 작업을 못 하게 되고,
  사용자의 로그인·탭·개인 데이터가 자동화에 섞인다.
- 브라우저 자동화 설정을 사용자 브라우저 프로필·확장을 쓰도록 바꾸지 않는다.
- 사용자 도움이 필요한 상황 — 로그인·재로그인, 2FA·기기 확인, CAPTCHA, 권한·SSO 동의,
  브라우저 연결 끊김, 파일 선택 창 같은 네이티브 대화상자, 인증 문제로 보이는 404/403 — 이면
  **즉시** 사용자에게 한 줄로 말하고 기다린다: 무엇이 필요한지(사이트·계정·어느 브라우저 창)와
  해 주면 이어서 할 일.
- 분리된 브라우저에 로그인이 필요하면 **그 브라우저 창에 로그인해 달라고** 요청한다. 사용자
  브라우저로 우회하지 않는다.
- 조용히 실패로 넘기거나 다른 경로로 우회하지 않는다. 비밀번호·토큰을 대신 입력하지 않는다.
- 서브에이전트에게 브라우저 작업을 맡길 때는 프롬프트에 "사용자 도움이 필요하면 멈추고 질문으로
  반환한다"와 "사용자 브라우저 사용 금지, 분리된 브라우저만 쓴다"를 명시한다.

## 문서 갱신과 lock

- 종료 시 `HANDOFF.md`/`CONTEXT.md`를 자동 갱신한다. history 나열이 아니라 "현재 상태 기록"
  으로 쓴다. (예: "AA 처리는 YY 동작으로 수행한다. 단, XX 동작은 ~ 이유로 금지." — "원래
  XX였는데 리뷰로 YY가 됨" 식의 이력 서술 금지.)
- `AGENTS.md` 같은 tracked 중요 문서는 직접 수정하지 않는다. 변경안을 diff로 제시하고 승인을
  기다린다.
- 공유 상태 문서를 수정하기 전 같은 경로의 `<파일명>.lock`을 확인한다. lock이 있으면 다른
  Agent의 갱신이 끝나(lock이 사라져) 뒤에 진행한다. 없으면 lock 파일을 만들고 수정을 마친 뒤
  즉시 삭제한다.

## 킷 소유 파일 무수정

- 설치된 킷 소유 파일 — `agent-kit-*` 스킬, 킷 Agent 정의(`.claude/agents/`·`.codex/agents/`의
  developer/review-killer/reviewer), 이 `AGENT-RULES.md`, `CLAUDE.local.md`,
  `AGENTS.override.md`, guard·hook 설정 — 은 **수정하지 않는다.** 선의의 "개선"도 금지다
  (수정 시 doctor가 드리프트로 감지하고 재설치·제거가 중단된다).
- 개선이 필요하면 그 내용을 사용자에게 보고한다. 반영은 킷 저장소(agent-project-kit)에서
  수정 후 재설치로만 이뤄진다.
- 예외는 mutable state인 `CONTEXT.md`/`HANDOFF.md` 둘뿐이며, 이 둘은 오히려 갱신이 의무다.

## 모델 정책

- 작업이 현재 모델로 감당하기 복잡하다고 판단되면 임의로 계속하지 말고 보고한다:
  "이 작업은 복잡해 보입니다. 상위 모델로 재가동하세요. (현재: <모델>)"
- Agent는 실행 중 스스로 모델을 바꿀 수 없다. 사용자가 상위 모델로 재가동하며, 재가동된
  Agent는 가동 절차(문서·작업 채널 정독)로 상태를 복원한다.

## 보고 정책

- 중간 산출물은 작업 채널(PR 코멘트, Jira 코멘트)에 남기고, 사용자에게는 종료 시점에 최종
  결과만 보고한다.
- 실행하지 않은 검증을 통과로 보고하지 않는다. 보고에는 실행 명령·구체 수치·출처를 붙인다.
